# PerfAgent (arXiv 2607.19653)

**Title:** PerfAgent: Profiler-Guided Iterative Refinement for Repository-Level Code Optimization
**Authors:** Ryan Deng, Yuanzhe Liu, Bastian Lipka, Yao Ma, Xuhao Chen, Tim Kaler†, Jatin Ganhotra† (MIT, RPI, IBM, Michigan State) — posted 22 Jul 2026 (v1)
**Local copy:** `../../ML_Peformance_AutoResearch/PerfAgent_2607.19653.pdf` (outside this repo's version control, kept for reference only)

## Problem

LLM coding agents already do well on correctness-oriented repository tasks (SWE-Bench-style issue resolution, feature implementation), but struggle at **repository-level performance optimization**: preserving behavior while genuinely improving runtime, not just passing tests.

The paper identifies three failure modes that keep agents from matching human-expert optimization patches:
1. Agents don't use profiling tools to full effect — they miss real bottlenecks, especially ones hidden behind abstraction layers or inside native extensions.
2. Agents stop optimizing after a shallow speedup instead of continuing to look for larger gains.
3. Agents test their changes too narrowly, so patches that look fast on the target workload can silently break edge cases or downstream code.

## Method — PerfAgent

A profiler-guided, verifier-in-the-loop workflow wrapped around an off-the-shelf coding agent, with three components:
- **Sampling profiler feedback:** runs a sampling profiler on the target workload and feeds the agent a curated hotspot summary (location, call context, share of runtime) so it can localize where time is actually spent, including inside native extensions.
- **Objective-driven loop controller:** refuses to accept the agent's first passing patch. After each submission it rebuilds, re-validates, and re-profiles the repo, then asks the agent to keep optimizing — retaining the fastest *correct* patch seen across attempts. This is iterative single-chain refinement with retries, not an explicit branching search.
- **Selective test stage:** re-runs only the curated test cases affected by the current change set, catching regressions cheaply and feeding failures back as feedback, so correctness isn't sacrificed for speed.

## Results

On two optimization benchmarks — GSO and SWE-efficiency-Lite:
- Rate of expert-matching patches (with GPT-5.1 as the underlying agent) more than doubles: GSO 19.6% → 39.2%, SWE-efficiency-Lite 26% → 74%.
- Surpasses an oracle best-of-five sampling baseline at substantially lower cost — the paper's headline claim is that the gains come from *better feedback*, not from throwing more test-time sampling at the problem.
