# ML Operators (算子): A Beginner's Primer

From-scratch explanation of what an "operator" is in deep-learning frameworks and compilers, written for someone new to ML. Compiled 2026-10-15 from a Q&A session; it is a learning note, not a reference spec. Operator-count figures are approximate and drift across framework versions.

## 0. One-sentence version

**An operator is the smallest "compute building block" in a deep-learning framework: it takes some tensors and produces new tensors according to a fixed mathematical rule.**

A neural network is essentially hundreds to thousands of operators chained together. Inference runs that chain forward; training also runs it backward.

## 1. What operators work on: tensors

A tensor is a **multi-dimensional array**:

| Rank | Example | Shape |
|---|---|---|
| 0-D | a scalar `3.14` | `()` |
| 1-D | vector `[1, 2, 3]` | `(3,)` |
| 2-D | matrix (e.g. a grayscale image) | `(28, 28)` |
| 4-D | a batch of color images | `(batch=32, channel=3, H=224, W=224)` |

Operator inputs and outputs are tensors.

## 2. What operators look like

```python
import torch
a = torch.tensor([1., -2., 3.])
b = torch.tensor([4.,  5., 6.])

torch.add(a, b)          # add      -> [5., 3., 9.]
torch.relu(a)            # ReLU     -> [1., 0., 3.]   (negatives become 0)
torch.sum(a)             # sum      -> 2.
torch.matmul(A, B)       # matrix multiply
torch.reshape(a, (3, 1)) # reshape: same values, new shape
```

Each of these is an operator. "Fancier" names like `relu`, `softmax`, `conv2d`, `layer_norm` are also operators, just with more complex rules.

## 3. A neural network is a graph of operators

A fully connected layer:

$$y = \text{ReLU}(xW + b)$$

breaks down into **3 operators**:

```
 x ──┐
     ├─[matmul]──┐
 W ──┘           ├─[add]──[relu]── y
 b ──────────────┘
```

This is a **computation graph**: nodes are operators, edges are tensors. A GPT-scale model is the same thing with hundreds of thousands of nodes, mostly repeated matmul / softmax / layernorm / add / gelu.

> **Core idea: model = operator graph. The job of a framework or compiler = execute that graph efficiently.**

## 4. The three layers of an operator: semantics, interface, implementation

The distinction beginners most often blur, and the basis for everything below.

| Layer | Question it answers | Example (matrix multiply) |
|---|---|---|
| **Semantics / definition** | What does it compute? Shape and dtype rules? | `C[i,j] = Σ_k A[i,k]·B[k,j]`; `(m,k) × (k,n) → (m,n)` |
| **Interface / signature** | How do users and the framework call it? | `torch.matmul`; underneath `aten::mm(Tensor self, Tensor mat2) -> Tensor` |
| **Implementation / kernel** | What code actually computes it on a given device? | CPU: MKL/OpenBLAS; NVIDIA GPU: cuBLAS or custom CUDA; TPU: code generated by XLA |

**Operator = the abstract "what to compute". Kernel = the concrete "how, on this hardware".** One operator can have many kernels (CPU, GPU, float32, bfloat16, ...).

## 5. What happens when you call an operator (PyTorch)

```
torch.add(a, b)
   │
   ▼
Python binding → C++ ATen library (PyTorch's operator library)
   │
   ▼
Dispatcher: inspects device, dtype, whether autograd must record, ...
   │
   ├── a on CPU        → CPU kernel
   ├── a on CUDA       → CUDA kernel
   └── a on XLA device → no immediate compute; recorded as a graph node and handed to XLA to compile
```

The **dispatcher** is the key concept: one operator name, routed to different implementations by device and dtype.

## 6. Operators must also run backward: backpropagation

Training needs gradients, so every operator defines a **backward** rule in addition to **forward**:

| Operator | Forward | Backward (given output gradient `g`) |
|---|---|---|
| add | `y = a + b` | `∂a = g, ∂b = g` |
| mul | `y = a · b` | `∂a = g·b, ∂b = g·a` |
| relu | `y = max(x, 0)` | `∂x = g` where x > 0, else 0 |
| matmul | `C = A·B` | `∂A = g·Bᵀ, ∂B = Aᵀ·g` |

**Autograd** records which operators ran during forward, then calls their backward rules in reverse order, chaining them with the chain rule. Adding a new operator to a framework usually means supplying its gradient formula too (and the backward is itself made of operators).

## 7. Operator categories

| Category | Examples | Notes |
|---|---|---|
| **Element-wise** | add, mul, relu, exp, gelu | Each position independent; simplest; **easiest to fuse** |
| **Reduction** | sum, mean, max, the sum inside softmax | Collapses a dimension |
| **Compute-heavy** | matmul, conv, attention | Most of a model's FLOPs; main target of hardware optimization |
| **Data movement / shape** | reshape, transpose, concat, slice, gather | Little or no math; change layout or select data |
| **Normalization** | layer_norm, batch_norm | Usually reduction + element-wise |
| **Control flow / other** | while, cond, RNG, sort | Hardest for compilers |

## 8. Operator sets: each system speaks its own "language"

| System | Operator set | Rough size |
|---|---|---|
| PyTorch | **ATen** | 2000+ (many redundant/convenience variants) |
| PyTorch 2.x | **Core ATen IR** / **Prims** | ~180 / fewer (trimmed for compiler backends) |
| ONNX | **ONNX opset** | ~180, versioned |
| XLA / JAX / TPU | **HLO / StableHLO** | ~100, deliberately small and orthogonal |
| TensorFlow | TF ops | 1000+ |

The size difference reflects a **design trade-off**:

- **Large set (ATen):** user-friendly and directly fast, but every new hardware backend must implement thousands of kernels.
- **Small set (HLO):** a backend only needs ~100 primitives; complex ops decompose into primitives and the **compiler** recovers performance.

> Research connection: **PyTorch → XLA migration is, underneath, translating ATen operators into HLO operators ("lowering").** If an ATen op has no lowering, PyTorch/XLA falls back to CPU, copying data between TPU and CPU, and performance collapses. Typical migration pain ("op not supported", recompilation from dynamic shapes) is fundamentally operator-level. See [Infeasibility-Aware Agents](../synthesis/Infeasibility_Aware_Agents_Fail_Fast_Idea.md) for a research idea built on detecting exactly these fallbacks.

## 9. Why operator fusion matters

```python
y = relu(x * 2 + 1)
```

**Naive execution:** 3 operators, 3 kernels:

```
read x  → [mul]  → write t1 to memory
read t1 → [add]  → write t2 to memory
read t2 → [relu] → write y to memory
```

On modern GPUs/TPUs **compute is fast; memory reads/writes are slow**. Element-wise ops spend most of their time moving data.

**After fusion:** 1 kernel:

```
read x → compute x*2+1 then relu in registers → write y
```

Memory traffic drops from 6 accesses to 2, often several times faster.

Automatically finding fusable operators and generating fused kernels is a core job of **deep-learning compilers** (XLA, TorchInductor, TensorRT). FlashAttention is essentially a hand-fused matmul + softmax + matmul.

## 10. Custom operators

When existing operators are missing (a new attention variant, a special quantization scheme) or too slow:

1. **Compose existing ops**: simplest, possibly slow.
2. **Write a Triton kernel**: Python-like GPU kernel language, moderate difficulty (TorchInductor also emits Triton).
3. **Write a CUDA / C++ kernel**: highest ceiling, hardest.
4. **Register with the framework**: `torch.library` to define the signature, kernels, gradient formula, and a "meta/fake" implementation for compilers (shape inference only, no real compute).

## 11. The big picture

```
  Model code (nn.Linear, attention, ...)
            │  made of
            ▼
     Operator graph   ← operator = semantics + interface
            │
     ┌──────┴────────┐
  Eager execution    Compiler (XLA / Inductor)
  Dispatcher         lowering → fusion → codegen
  one kernel per op     │
     │                  ▼
     └──────►  Kernels (code that actually runs)
                CPU / GPU / TPU
```

## 12. Suggested learning path

1. **Feel operators by hand:** write a two-layer MLP in NumPy/PyTorch without `nn.Module`; list which operators you used.
2. **See the graph:** export a small model with `torch.fx.symbolic_trace` or `torch.export` and print its operator list.
3. **Understand autograd:** Karpathy's **micrograd** video (~2 h), implementing scalar autograd yourself — makes "operator + backward rule" concrete.
4. **Understand performance:** Horace He, "Making Deep Learning Go Brrrr From First Principles" — compute-bound vs. memory-bound, and why fusion helps.
5. **Compiler view:** in JAX, `jax.jit(f).lower(x).as_text()` to see StableHLO; in PyTorch/XLA, set `XLA_SAVE_TENSORS_FILE` to dump the HLO graph.
6. **First kernel:** follow the official Triton tutorials (vector add, fused softmax).

Step 5 is closest to the future Google Core ML Frameworks & Compiler work (see [Hosting Interns and Publishing as a Google SWE L4](Google_L4_Intern_Hosting_And_Publishing.md) for team context); steps 1–4 first make HLO readable.
